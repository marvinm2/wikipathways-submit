# Web UI review — `wikipathways-curator`

*2026-07-27. Produced by a five-lens review (accessibility, visual design, responsive, client-side
interaction, copy/IA), each finding put through an adversarial verification pass that refuted 13 of
65. Items 1-8, 12, 18, 20, 23, 28 and 30 were fixed in `55d218f`; the rest stand as a backlog.*

Ranked by how much each defect hurts a real user. Duplicates across lenses are merged; the file:line given is the canonical place to fix it.

---

### 1. Pressing Enter in the WPID field reloads the page and discards the whole update form
`static/app.js:143` (form at `templates/index.html:80`) — **high**

`#update-form` is a real `<form>` whose only action button is `type="button"`, wired through a `click` listener. With one text field and no submit listener, the browser performs implicit submission on Enter: it navigates to `/` with no query string. Typing `WP554` and hitting Enter — the most natural thing a person does in a one-field form — resets to the "New pathway" tab and silently throws away the chosen GPML file, the "What changed?" checkboxes and the details textarea. Nothing explains why.

**Fix:** bind the handler to the form's `submit` event instead of the button's `click`, or at minimum add `updateForm.addEventListener('submit', e => e.preventDefault())` so Enter runs the same guarded upload path.

### 2. A 401 or 502 from the WPID lookup is reported as "does not exist yet"
`static/app.js:175` (mirror bug at `static/app.js:120`) — **high**

`r.ok ? r.json() : { state: 'absent' }` collapses every non-2xx into *absent*. `/api/pathways/{wpid}` (`app/main.py:606`) returns **401** on an expired session and **502** when the GitHub read fails (`app/main.py:621`). In both cases the submitter is told "WP554 does not exist yet — use the New pathway tab." Following that instruction submits an existing pathway as new, burning a fresh WPID and opening a duplicate-content PR — precisely the failure this app exists to prevent. The blur handler hides the status line entirely on error, so there is no earlier warning either.

**Fix:** branch on status — 401 → "Your session expired, log in again" and stop; any other non-2xx → `describeError(r.status, body)` and abort; treat only a real 200 with `state === 'absent'` as absent. Same three-way branch in the blur handler.

### 3. Clicking a checklist chip permanently erases that item's explanatory note
`static/app.js:258` — **high**

`postForm(...)` sends `key` and `state` but no `note`; the endpoint declares `note: str = Form("")` (`app/main.py:659`) and `set_checklist_item` assigns it unconditionally (`app/review/service.py:290`). The auto-derived notes — "Not relevant — unchanged in this update." (`app/review/checklist.py:197`) and the auto-check explanations — are destroyed the first time any curator clicks Pass/Fail/N-A. They are gone from the DB, from the mirrored PR comment and from every other curator's view. `reconcileChecklist` never touches `.checklist__note`, so the deleted text stays on screen until reload and then vanishes with no explanation.

**Fix:** make omission non-destructive server-side — `note: str | None = Form(None)`, assign `item["note"]` only when not None. A state click should not be a note edit.

### 4. The render disappears from every review that is not `open`, replaced by a spinner that never resolves
`app/main.py:299`, rendered at `templates/dashboard.html:64`, `:77`, `:79` — **high**

`_review_view` builds `preview` only `if r.status == ReviewStatus.OPEN`; the template's None branch is the *loading* state (pulsing dots, "Preview generating…" / "Rendering…"). So on the **Changes requested**, **Merged** and **Closed** filters every card animates forever, even though the SVGs are sitting in `preview-cache/<pr>/`. Changes-requested is an active state a curator must return to, and it loses the one artifact the app exists to put in front of them; a settled queue looks permanently stuck, and the resolution banner is pushed below a 19rem placeholder.

**Fix:** compute `preview` for any status whose SVGs exist — drop the `if` and let `PreviewService.status()` decide, or gate on `OPEN | CHANGES_REQUESTED` at minimum. Add a static "no preview kept" branch for genuinely absent renders. The docstring at `app/main.py:294` also needs correcting: `changes_requested` has no resolved banner.

### 5. "Preview generating…" promises background work that never runs
`templates/dashboard.html:79` (and `:34`) — **high**

`_render_preview` runs synchronously inside submit/update (`app/main.py:479`, `:538`) and always writes either an SVG or a `render-failed` marker. Nothing renders later, and no JS polls. So `status == 'pending'` means *this will never be rendered* — cache wiped by a redeploy onto another node, `mkdir` failed, review registered outside the write path — yet the copy plus three animated dots says it is in progress. A curator waits and reloads indefinitely, with no hint that re-uploading is the only remedy; if `require_preview_check` is on, approve also 409s with no visible cause.

**Fix:** rename the pending state to something truthful and actionable — "No render on file for this pull request. Ask the submitter to re-upload, or open the PR for the validation tables." Drop `preview__dots` so it stops reading as in-progress.

### 6. The submitter never sees the changes-requested instruction — it is inside the curator-only branch
`templates/dashboard.html:186` (inside `{% elif is_curator %}` at `:183`) — **high**

The banner "Changes requested · waiting for the submitter to revise. Re-uploading re-opens review." only renders for curators. The submitter falls into the `{% else %}` at `:210` and gets "Only curators can update the checklist, assign a reviewer, or approve." They see a badge, some failed checklist rows, and no statement that anything is expected of them or what to do. The revise loop (`/api/pathways/{wpid}/revise`) works but is completely undiscoverable from the UI.

**Fix:** move the banner out of the `is_curator` branch and word the submitter-facing version with the actual next step: "A curator asked for changes. Fix the GPML and re-upload it under Submit → Update existing with this WPID — it reuses this pull request and puts the review back in the queue," linking to `/` with the WPID prefilled.

### 7. The pathway check-out conflict is shown to a biologist as a raw JSON blob
`static/app.js:32` — **high**

`describeError` handles an array `detail.errors` and a string `detail`, then falls through to `JSON.stringify(detail)`. The update endpoint raises exactly the object case: `detail={"reason": ..., "held_by": ...}` (`app/main.py:519`). The headline failure mode of the update flow renders as `Error 409: {"reason":"...","held_by":"alice"}` — a debug dump with no mention that the lock expires, that they can wait, or that a curator can release it.

**Fix:** add `else if (detail && detail.reason)` before the stringify fallback, and special-case 409 on the update path: "WP554 is currently being edited by @alice. Only one edit at a time is allowed so the two versions cannot conflict. Try again once their pull request is merged or closed, or ask a curator to release it."

### 8. Previews are a scroll trap: the wheel is always hijacked and touch gestures go nowhere
`static/app.js:381` and `static/app.css:688` — **high**

The `wheel` listener is `{ passive: false }` and calls `preventDefault()` unconditionally, at any scale. Each queue card carries one or two 19rem preview frames (two stack to ~608px), so scrolling the queue stops dead the moment the cursor crosses a diagram and the diagram zooms in instead, staying zoomed after the pointer leaves. On touch it is worse: `.zoom__viewport { touch-action: none }` hands the gesture to JS, but the pan handler bails at `scale <= 1` (`app.js:386`), so a swipe over a preview neither scrolls the page nor pans the image — on a phone most of the card is simply dead.

**Fix:** `if (!e.ctrlKey && scale <= 1.001) return;` before `preventDefault`, and `.zoom__viewport { touch-action: pan-y; }` with `.zoom--zoomed .zoom__viewport { touch-action: none; }` (the class is already toggled at `app.js:363`).

### 9. The disabled "Approve & merge" button is dimmed twice and lands at ~1.8:1
`static/app.css:246` + `:273` — **high**

The template sets both `disabled` and `aria-disabled="true"` whenever a required item is unticked — the state on arrival. `.btn:disabled { opacity: 0.5 }` and `.btn--approve[aria-disabled="true"] { color: var(--ink-faint); background: var(--surface-2) }` stack, resolving to roughly #C0C0C0 on #FDFDFE, about 1.8:1 (≈2.2:1 in dark mode). The dashboard's primary action reads as a blank grey slab — a curator cannot see what it says or that it is a button, only that something is missing.

**Fix:** add `opacity: 1` to the `[aria-disabled]` approve rule (or scope the generic opacity rule to `.btn:not(.btn--approve)`), and use `--ink-muted` rather than `--ink-faint` for the disabled label.

### 10. Toast variants hardcode white text on tokens that go pale in dark mode
`static/app.css:956` — **high**

`.toast--error { background: var(--brick); color: #fff }` and `.toast--success { background: var(--moss-strong); color: #fff }`. In dark mode `--brick` is #e2897d (2.6:1 with white) and `--moss-strong` is #adbcff (1.8:1 — effectively invisible). Toasts are the app's *only* error channel — "pathway is locked", "Choose a .gpml file first" — so a dark-mode user gets a coloured rectangle with no readable message. The base `.toast` at `:946` gets this right with `--ink`/`--bg`; the two variants are the outliers.

**Fix:** use tokens that flip — `var(--moss-contrast)` for success, a new `--brick-contrast` for error — or keep the base ink-on-bg treatment and tint only the left border.

### 11. Errors exist only in a toast that self-destructs after six seconds
`static/app.js:24` — **medium**

`describeError` joins the server's validation reasons into a semicolon-run and `setTimeout(..., 6000)` removes it; nothing is written into the page (the `#result-card` at `:91` is populated on success only). A GPML rejected with several validation errors gives the submitter one six-second read of a long string with no way to pause, re-read or copy it — a WCAG 2.2.1 failure that hits magnifier users, slow readers and anyone who looked away, and it is exactly the moment they most need the detail.

**Fix:** render errors into the persistent `#result-card` / `#update-result` (`hidden=false`, `role="alert"`) in addition to the toast, and skip the auto-dismiss timer when `type === 'error'`.

### 12. Both file inputs have no programmatic label
`templates/index.html:66` and `:94` — **medium**

Neither `#new-file` nor `#update-file` has a `<label for=…>`, an `aria-label`, or a wrapping label — there is no `for=` attribute anywhere in `templates/`. A screen-reader user tabbing the form hears "button, file upload" with no indication of what to upload; the update input does not even carry the `aria-describedby` hint the new-pathway one has. This is the primary control of the app's primary task.

**Fix:** wrap each input in a `<label>`, or add `<label for="new-file">GPML file</label>` / `<label for="update-file">Edited GPML file</label>`, matching the existing `.wpid-field` / `.note-field` pattern.

### 13. The site header overflows a phone viewport and cannot wrap
`static/app.css:146` — **medium**

`.site-header__inner` is a nowrap flex row with no `flex-wrap` and no media query (the only breakpoints in the file are 720px for `.steps` and 640px for `.preview`). Nothing can shrink: the logo is `flex: none` at ~105px, `.site-header__portal` adds "Pathway portal", and `.site-header__who` (`:202`) is another nowrap row holding `@login` plus the CURATOR badge with no `min-width: 0`. At 375px the row is ~327px of space against ~185px of brand plus 165–350px of identity (GitHub allows 39-character logins): the document gets a horizontal scrollbar and Log out is pushed off-screen. When it does fit, `.site-header__nav`'s wrap stacks Submit / Dashboard / @login / Log out onto separate lines, giving a `position: sticky` bar ~150px tall that covers a quarter of every screen.

**Fix:** `@media (max-width: 720px) { .site-header__inner { flex-wrap: wrap; row-gap: .4rem; } .site-header__portal { display: none; } .site-header__nav { margin-left: 0; width: 100%; } .site-header__who { min-width: 0; overflow-wrap: anywhere; } }`.

### 14. A zoomed preview can only be panned with a pointer
`static/app.js:385` — **medium**

Panning is bound to `pointerdown`/`pointermove` only. `.zoom__viewport` has `overflow: hidden` (`app.css:687`), is not focusable, and has no key handler. A keyboard-only curator can press "+" up to 8× and then see only the centre of the diagram — no scrollbars, no arrow keys, no way to reach the rest. Reading node labels in a dense pathway is the core review task.

**Fix:** give `.zoom__viewport` `tabindex="0"` plus a role and label, and handle Arrow keys (Home to reset) by adjusting `tx`/`ty` in `initZoom`; `apply()` already re-renders.

### 15. The `changes_requested` status badge has no CSS variant
`static/app.css:313` — **medium**

`dashboard.html:48` emits `badge--{{ r.status }}`, and `ReviewStatus` includes `changes_requested` (`app/models/__init__.py:73`), but only `--new`, `--update`, `--open`, `--merged`, `--closed`, `--curator` exist. On the "Changes requested" tab every chip falls back to the bare `.badge` rule — transparent border, no background — rendering as loose uppercase text jammed against the "Update" pill. It is the one queue tab where the status column visually breaks.

**Fix:** `.badge--changes_requested { background: var(--amber-tint); color: var(--amber); }`.

### 16. Update cards have no failed-render state — they spin on "Rendering…" instead
`templates/dashboard.html:25` (macro) / `:64`, `:68` (call sites) — **medium**

`preview_frame` only knows *url* or *no url*, and both call sites pass `None` for anything that is not `status == 'ready'`. The new-pathway branch has a real failed state ("Could not draw this pathway from its GPML.", `:75`); the update branch does not. So an update whose GPML the renderer refuses shows two animated frames indefinitely — 38rem of pulsing boxes on mobile — and the curator cannot distinguish a broken file from a slow one. The strongest available signal that a submission is malformed is swallowed.

**Fix:** pass `r.preview.status` into `preview_frame` and give it the same `.preview__failed` branch as the solo frame.

`templates/dashboard.html:90` — **medium**

`datanodes_url` is `{pr_url}/files` (`app/main.py:307`). ### 20. `hidden` on the request-changes panel is defeated by `display: flex`
`static/app.css:885` (markup at `templates/dashboard.html:206`) — **medium**

An author-origin `display: flex` beats the UA stylesheet's `[hidden] { display: none }`, so `<div class="changes-panel" hidden>` is never hidden. On every open card the note textarea and a live "Send request" button sit permanently on screen and in the tab order, so a keyboard or screen-reader curator tabs through an unlabeled textarea and a live action on every card in the queue and can fire a request-changes on a review they never opened. Meanwhile the "Request changes" button (`app.js:302`) appears to do nothing but yank focus with no announced context.

**Fix:** add `[hidden] { display: none !important; }` to the reset near `app.css:97`, or scope the rule to `.changes-panel:not([hidden])`.

### 21. `--ink-faint: #828282` is below AA for every text role it carries
`static/app.css:22` — **medium**

3.7–4.0:1 on `--surface-2` and white, under the 4.5:1 needed at the 13–14px sizes it drives: the preview `figcaption` "Before"/"After", `.checklist__note`, `.checklist__title`, `.state-pill--pending` (the default state of every checklist row), `.datanodes__missing` "not annotated", `.datanodes th`, the field labels, `.preview__empty` text and the footer. Low-vision curators cannot reliably read which frame is Before or which data nodes are unannotated — the exact information the review turns on. It is also a pure neutral inside an otherwise blue-tinted ink ramp (#1c2634, #5a6472), so the caption layer visibly belongs to a different stylesheet.

**Fix:** retint and darken, e.g. `#6b7684` in light mode; keep a lighter value for dark. Re-check `.state-pill--pending` after.

### 22. Hardcoded status hexes never flip for dark mode
`static/app.css:456-458`, `:907`, `:858-859`, `:744` — **medium**

Four one-off palettes ignore the `prefers-color-scheme: dark` block that repaints `--surface` to #182029: the WPID lookup states (`#15803d` / `#b45309` / `#b91c1c`, 2.8–3.7:1 on dark), the "Changes requested" resolution banner (`#b45309` on a theme-following mix, ~2.6:1, while its `--merged` and `--closed` siblings flip correctly), the selected Fail and N/A chips (`#fff` on #e2897d and #a7bcc4 — 2.6:1 and 2.0:1, so two of three chips blank out the moment they are chosen, while Pass uses `--moss-contrast` and stays legible), and `.datanodes__row--unmapped`'s raw `#d97706`. The WPID message ("WP554 does not exist yet. Use the New pathway tab.") is the single most consequential sentence on the submit page and the hardest to read.

### 23. Long unbroken strings in notes and descriptions overflow the card and the page
`static/app.css:734` — **medium**

### 24. The detail page's taller viewport does not make the diagram any bigger
`static/app.css:681` — **medium**

`.preview__frame img { width: 100%; height: 19rem }` also matches the zoom image, because `.zoom .zoom__img` (`:696`) only sets `max-width`/`max-height`. On `/dashboard/{pr}` the viewport grows to 30rem (`:693`) but the image stays 19rem and is centred, so clicking "open full review" — whose entire purpose is a bigger render — yields the same-size pathway plus ~5.5rem of dead grey above and below. `.preview__empty` / `.preview__failed` (`:759`) are likewise pinned at 19rem, so pending and ready frames on the same page are different heights, and `measure()` (`app.js:344`) reads the frame box rather than the fitted image as the zoom basis.

**Fix:** scope the legacy rule to `.preview__frame > img` (every preview goes through the `zoomable()` macro), or drop the fixed height and let `.zoom__img { max-height: 100% }` size from the viewport; add a 30rem override for the expanded empty/failed blocks.

### 25. Review cards have no accessible name; the detail page has no `h1`
`templates/dashboard.html:40` and `templates/review_detail.html:14` — **medium**

Each PR is an `<article>` identified only by a WPID inside a `<div class="tag-wpid">` — no heading, no `aria-label`. Working a queue of 20 submissions, a screen-reader curator cannot jump card to card, and every card sounds identical (same "Assign reviewer" select, same Pass/Fail/N-A chips). Heading order is also inverted: `<h4>Submitter note</h4>` (`:99`) sits directly under the page `<h1>` (`:217`) and *before* `<h3>Curation checklist</h3>` (`:160`). The detail page renders a breadcrumb, a lede and the card macro with no `<h1>` at all, so pressing "1" on a single review finds nothing.

**Fix:** give the article a heading (`{{ r.wpid_str }} — New pathway / Update (PR #{{ r.pr_number }})`) in `review-card__head` with `aria-labelledby` on the `<article>`, demote the meta-panel headings to h3/h4, and add an `<h1>` to `review_detail.html`.

### 29. The WPID lookup response overwrites the "Submitting…" label mid-upload
`static/app.js:127` (also `:131`) — **low**

Blur fires before click when a user tabs or clicks straight from the WPID field to the button, so an in-flight lookup can resolve *after* the click handler set the label to "Submitting…" and disabled the button. The label flips back to "Submit update" while the button is still disabled: the user sees an idle button, assumes the click was lost, and clicks again with no response. `reset()` then restores a label captured before the lookup landed, so the button can end up mislabelled for a pending-new pathway.

### 34. Log out silently does nothing when the request fails

### 35. The sticky header covers the target of the skip link

## Overall

This is a genuinely well-built server-rendered UI, and the parts that matter most are right. The information architecture matches the job: a two-tab submit stepper for people who have never used git, a queue whose cards carry the before/after render, the checklist, the metadata panel and the approve action in one place, so a curator never has to leave for GitHub. The design system is real — tokens, tints, a consistent badge/pill/chip vocabulary, a dark-mode block, a `.visually-hidden` utility, a skip link, `aria-pressed` on the chips, `aria-disabled` alongside `disabled` on approve. The client-side reconciliation of checklist state instead of a page reload, and the app-side SVG renderer that removes the CI wait entirely, are the two decisions that most improve the reviewer's day. Most findings above are one-line fixes to an otherwise coherent whole, not structural problems.

The single most valuable thing to change is the preview lifecycle — findings 4, 5 and 16 together. The render is the entire premise of this app ("reviewers approve unreadable XML" is problem #1 from the audit), and right now it is present only for `open` reviews, an unrenderable GPML is indistinguishable from a slow one, and a cache that vanished on redeploy animates a promise it will never keep. Fixing that means computing the preview for every status whose SVGs exist, threading the real status into `preview_frame` so `failed` says so, and renaming `pending` to an honest, actionable message with the spinner removed. That one change turns three tabs of the dashboard from "looks broken" into "works", and it is a couple of dozen lines across `app/main.py:299` and the macro at `templates/dashboard.html:25`.
